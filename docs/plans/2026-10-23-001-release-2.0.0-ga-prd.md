## 1. Problem Statement

**rc1 is version strings and changelog only, and it lacks the latest fixes.** `2.0.0rc1` is two commits on top of main `1f801b4`: `2400936` ("cut 2.0.0rc1") and `d396603` **[V]** (`git log -3`). It does not contain the 11 authority-reliability commits on `origin/main` (`69410b7^..976a244`, #177): `git rev-list --count HEAD..origin/main` → 11, and `git merge-base --is-ancestor 976a244 HEAD` → exit 1 **[V]**. Commit subjects and new tests in that range target audit HIGH findings N1/N2, but this PRD did not run those tests, so their closure is **[I]**.

**The audit says not to ship, and the pipeline is expected to fail.** The latest audit verdict is **REQUEST CHANGES**, with **9 open HIGH** ("8 new + 1 prior still present") and 21 open MEDIUM findings (`main-checkout/audits/project-review-2026-10-22.md:5`) **[V]**. Audit finding N26 reports that the publish test job cannot pass. `publish.yml:19` installs only `.[dev]`, and `publish.yml:25-28` runs all of `tests/` without ignoring the PostgreSQL suite **[V]**. The resulting failure itself was not run here **[I]**.

**The upgrade docs don't cover the breaks.**
- **55 Breaking bullets plus one authority-store data-break note**, 56 breaking items in total (`CHANGELOG.md:9-454`; `grep -cE '^\s*- \*\*Breaking'` → 55; the data note is at `CHANGELOG.md:26`) **[V]**.
- **No 2.0 section in MIGRATION.md.** Its first heading is "Migrating to constitutional_swarm v1.1.0" (`MIGRATION.md:1`) **[V]**.
- **An undocumented break of the stable `SwarmExecutor` API.** It was introduced by `eea8477` (2026-08-28, "seal APCC authority and GCB projection") **[V]**. That is APCC/GCB feature work, which the changelog says it does not cover (`CHANGELOG.md:22-24`) **[V]**. Other breaks from that work may also be undocumented **[I]**.
- **An authority-store data break with no migration tool** (`CHANGELOG.md:22-41`) **[V]**.

This would be the first PyPI publication since 0.1.1 (`CHANGELOG.md:9-21`) **[V]**, so many upgraders will start from 0.1.1 rather than 1.1.x **[I]**.

## 2. Goals (outcomes)

1. **Users are not exposed to issues already fixed on main.** Acceptance is in P0-1.
2. **Every file on PyPI for 2.0.0 is byte-identical to the artifact that passed the gated run.** Acceptance is in P0-2 and P0-7.
3. **The residual security risk at GA is disclosed truthfully.** No HIGH finding ships without a recorded disposition, and the release notes make no claim that an accepted finding contradicts. Acceptance is in P0-3.
4. **An upgrader from 0.1.1 or 1.1.x can migrate using only the shipped docs.** A non-author validates this with a guided upgrade. Acceptance is in P0-5 and P0-8.
5. **Authority-store operators know before upgrading whether their store will reopen, and that the upgrade is one-way.** They should not first learn it from a generic `semantic validation failed`. Acceptance is in P0-4.

## 3. Non-Goals

| Non-goal | Rationale |
|---|---|
| **An in-place migration tool for authority stores** | Rewriting ids would re-hash the trust-log chain. That needs a replay/re-seal design that does not exist (`DECISIONS.md:643-645`) **[V]**. GA ships a documented rebuild path instead. |
| **Closing all 21 MEDIUM and 48 unverified LOW findings** | GA requires a disposition for each MEDIUM (P1-3), not a fix. LOWs are post-GA unless promoted (Q7). |
| **Clearing the ruff format debt** | CLAUDE.md requires a dedicated formatting-only change, kept out of behavioural patches **[V]**. |
| **Publishing forensic-benchmark or monotonic-MAS numbers** | N4, N19, N20 and the prior leak are open, and `roadmap/TASKS.md:33` puts benchmark integrity under "Later" **[V]**. |
| **Migrating Bittensor to v11** | `bittensor>=7.0,<11` is a deliberate bound, and v11 is "a separate project" (`pyproject.toml:52-57`) **[V]**. |
| **Any compliance, certification or regulatory claim** | This is out of scope, and the GA notes must not imply one (Q10). |

## 4. User Stories

### 4.1 Library integrator upgrading from 1.1.x (or 0.1.1)
- **As an integrator**, I want a single 2.0 migration guide with before/after code, so I can upgrade without reading 56 breaking items.
- **As an integrator using `SwarmExecutor`**, I want the governed-claim break documented, so my code does not fail at runtime without warning. Three things changed **[V]**:
  - The constructor raises `TypeError` on `boundary=`/`trusted_admin=` (`swarm.py:334-338`).
  - `claim()` requires a `SignedAttemptAuthorization` (`swarm.py:607-608`).
  - `submit()` always raises `GovernanceBypassDenied` (`swarm.py:646-651`).
  
  None of this is in the CHANGELOG, because the change came from `eea8477`, outside the changelog's scope (`CHANGELOG.md:22-24`).
- *Edge:* the integrator upgrades from **0.1.1**, so the 1.0.0 and 1.1.0 changes are also new to them (`CHANGELOG.md:9-21`) **[V]**.
- *Edge:* the integrator still uses `ACGS_SIGNING_KEY`. It is read at `governed_handoff.py:775,796,803`, and no warning was seen there **[V]**. The integrator wants a runtime warning and a removal version.
- *Error:* the integrator verifies a v1 `MeshProof`. It returns `False` unless `allow_legacy_v1=True` (`CHANGELOG.md:~144-185`) **[V]**. This is one of the development-only "Explicit opt-ins" listed in `CHANGELOG.md:416-453` **[V]**.

### 4.2 Operator running the APCC authority store (SQLite / PostgreSQL)
- **As an operator**, I want to learn before upgrading whether my store predates C32. Today such stores fail with a generic `semantic validation failed` while the schema stays at 3 (`CHANGELOG.md:22-41`; `sqlite_store.py:142-143`) **[V]**.
- **As an operator**, I want a documented backup and rebuild procedure. No migration tool exists **[V]** (a grep of `scripts/`, `Makefile` and `apcc/` found none).
- **As an operator**, I want to know whether the upgrade is one-way, and which other persisted formats need action. Other versioned stores exist, for example the settlement `schema_version` (`MIGRATION.md:117`) **[V]**. Whether 1.x can read back 2.0-written data is not documented **[I]**.
- *Edge:* if schema v4 ships, **every** v3 store becomes unopenable with `schema version is incompatible`, including valid post-C32 stores (`sqlite_store.py:4187-4188`; `postgres_store.py:3157-3158`) **[V]**.
- *Edge:* mixed-version writers on one store are unsafe (`CHANGELOG.md:36-41`) **[V]**. This should be stated as an upgrade-ordering rule.
- *Error:* SQLite is opened under lock contention. Any `OperationalError` at connect maps to "not provisioned" (`roadmap/sqlite_store.py` ~4117-4132; not exercised) **[I]**.
- *Error:* PostgreSQL crashes during outbox recovery. PG writes one batch-level `outbox-delivered` audit row after the loop (`roadmap/postgres_store.py:4518`) **[V]**. The roadmap SQLite code instead writes a per-event audit (`roadmap/sqlite_store.py:3949`, ~3940-3970) **[V]**. rc1's SQLite has the same batch-level behaviour as PG (`sqlite_store.py:3954-3968`) **[V]**. Whether deliveries can be left unaudited after a mid-batch crash is **[I]**.

### 4.3 Release maintainer
- **As the maintainer**, I want `publish.yml` to pass on the GA commit. Today audit finding N26 says it cannot (`publish.yml:19,25-28`) **[V]** config; failure **[I]**.
- **As the maintainer**, I want a written GA checklist and a rollback runbook. The only launch checklist found covers the Rust protocol **[V]** (`docs/internal` listing). `grep -rniE 'yank|rollback'` over `.github`, `Makefile`, `docs` and `SECURITY.md` finds no release-rollback text **[I]** (reviewer-run, not re-run).
- **As the maintainer**, I want the published artifacts built and tested from the gated commit. The local `dist/*2.0.0rc1*` files have mtime 2026-10-22 01:14:55, about 50 s *before* `2400936` was committed (01:15:45). They were built from a working tree carrying the rc1 bump, before #177 **[V]** (`ls -l --time-style=full-iso dist`; `git log`). `publish.yml` rebuilds anyway (`publish.yml:39-50`) **[V]**.
- *Edge:* the `release: published` trigger has no prerelease filter (`publish.yml:3-5`) **[V]**, so a GitHub pre-release for rc2 would upload it to PyPI.
- *Edge:* `tla-check.yml` is path-filtered (`tla-check.yml:3-22`) **[V]**, so a version-only release PR does not run TLC.

### 4.4 Security reviewer / auditor
- **As a reviewer**, I want each open HIGH and MEDIUM ID mapped to a fixing commit or a recorded acceptance, so the GA notes can state the residual risk truthfully.
- **As a reviewer**, I want any change to the frozen B2 pair (`postgres_store.py`, `tests/test_apcc_postgres.py`) re-reviewed and its hashes re-pinned, as after C32 (`DECISIONS.md:651-656`) **[V]**.
- **As a reviewer**, I want a dependency vulnerability scan on record. No workflow runs one (`security.yml:3-36`) **[V]**.
- **As a reviewer**, I want the provenance of the published artifacts checked. Every action in `publish.yml` is pinned by tag, not by SHA (`publish.yml:14,15,46,61,66`), and no `attestations:` input is set **[V]**. Whether the default trusted-publisher attestations are produced was not checked offline **[I]**.

### 4.5 Research user
- **As a research user**, I want to know that DP sigma values and `DiscreteGaussianSampler` streams changed, and that the MCFS rule-set hash moved from `4b9636ce4710779f` to `ebcb7caa26e6abfb`, so I don't mix results across versions (`CHANGELOG.md:~306-310, 349-351`) **[V]**.
- *Edge:* monotonic-MAS runs need new run ids, and B5 state must be recreated. No procedure is documented (`CHANGELOG.md:322,332`) **[V]**.
